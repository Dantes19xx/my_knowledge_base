# ⚖️ Компромиссы при внедрении распределённого трейсинга

## 📌 Технические компромиссы

| Аспект                              | Компромисс                                                                                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Производительность**              | Трассировка требует сериализации, передачи и экспорта спанов. На высоконагруженных сервисах может добавлять ощутимый overhead.                   |
| **Объём данных**                    | Tracing генерирует большой поток данных. Необходимо настраивать сэмплирование, иначе возможна перегрузка хранилища ([[Jaeger]], Tempo).          |
| **Сложность внедрения**             | Требуется интеграция [[OpenTelemetry]] SDK во все сервисы, настройка прокидывания trace-контекста, особенно в асинхронных системах (RMQ, Kafka). |
| **Сложность поддержки**             | UНеобходима поддержка инфраструктуры: OTEL Collector, backend (Jaeger/Tempo), визуализация ([[Grafana]]), мониторинг их состояния.               |
| **Непрозрачность без визуализации** | Без настроенной визуализации и нормальной агрегации трейсинг становится "мёртвым" — данные есть, но пользы мало.                                 |

---

## 📌 Когда можно отказаться от трассировки

| Сценарий | Почему можно отказаться |
|----------|--------------------------|
| **Простой или односвязный сервис** | Нет межсервисных вызовов — достаточно логов и базовых метрик. |
| **Вспомогательные задачи или фоновые джобы** | Например, обновление кэша или экспорт отчётов, не влияющие на пользовательский опыт. |
| **Нет инфраструктуры для трейсинга** | Нет ресурсов на поддержку Collector'а и backend'а — трассировка будет неэффективной. |
| **Низкая частота запросов** | Если сервис вызывается редко, и ошибки легко локализуются — трейсинг необязателен. |
| **Пилотный/временный сервис** | Не стоит тратить время на интеграцию в MVP или временное решение. |

---

## ✅ Как компенсировать отсутствие трейсинга

- Улучшить логирование: добавить `trace_id`, `request_id`, `correlation_id` в логи
- Добавить метрики (Prometheus): время выполнения, частота ошибок, latency
- Использовать APM (если доступно): NewRelic, Datadog, Elastic APM

---

## 🟢 Общая рекомендация

Трассировка нужна там, где:
- есть **распределённость** (много API, очереди),
- важна **скорость устранения инцидентов**,
- и есть **ресурсы** на инфраструктуру.
