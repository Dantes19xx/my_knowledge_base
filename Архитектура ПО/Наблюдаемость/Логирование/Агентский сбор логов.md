## 🛰 Агентский сбор логов (Log Shipping)

### 🧱 Суть подхода

**Агентский сбор логов** (log shipping via agents) — это стратегия, при которой специальные **агенты** устанавливаются на серверах (или в контейнерах), чтобы **собирать, обрабатывать и отправлять** логи в централизованную систему (например, [[Elasticsearch]], [[Loki]], CloudWatch, etc).

> 📦 Приложение просто пишет логи (в [[stdout]] или файл), а агент берет на себя доставку, фильтрацию, буферизацию и пересылку.

### ✅ Преимущества

| Преимущество | Описание |
|--------------|----------|
| **Централизация** | Все логи из разных сервисов и машин собираются в одну систему. |
| **Надежность** | Буферизация, ретраи, контроль доставки. |
| **Гибкость** | Возможность фильтровать, парсить, обогащать логи на лету. |
| **Масштабируемость** | Можно собирать логи с тысяч хостов. |
| **Изоляция** | Приложение не зависит от системы логирования. |

### 🔧 Основные агенты

| Агент          | Подходит для                 | Особенности                                              |
| -------------- | ---------------------------- | -------------------------------------------------------- |
| **Fluent Bit** | Kubernetes, [[Docker]], edge | Лёгкий и быстрый (на C), популярный в K8s                |
| **Fluentd**    | Linux-сервера, Cloud         | Богатый плагинами, более тяжёлый                         |
| **Filebeat**   | Elastic Stack                | Прост в настройке, хорошо работает с journald            |
| **Vector**     | High-performance, гибрид     | Поддерживает множество источников/выходов                |
| **Promtail**   | Loki                         | Часть стека [[Grafana]] Loki, хорошо работает с journald |

### 🧪 Пример: Filebeat + Elastic

#### filebeat.yml

```yaml
filebeat.inputs:
  - type: log
    paths:
      - /var/log/myapp/*.log

output.elasticsearch:
  hosts: ["http://elasticsearch:9200"]
  ```

### 📦 Где обычно агенты запускаются

- На каждом **узле кластера** (daemonset в Kubernetes)
    
- Как **боковой контейнер** рядом с приложением
    
- На **bare-metal серверах** в виде `systemd`-сервиса
    

### 📁 Что могут собирать

|Тип источника|Примеры|
|---|---|
|Файлы|`/var/log/*.log`, `application.log`|
|journald|`systemd`-логи|
|stdout/stderr|Из контейнеров (в K8s — через log-driver)|
|Сетевые порты|Syslog, TCP, UDP источники|
|Метки и env|Kubernetes labels, Docker labels|

### 🔗 Целевые системы (куда отправляют)

| Название        | Тип                          |
| --------------- | ---------------------------- |
| Elasticsearch   | Full-text поиск, [[Kibana]]  |
| Grafana Loki    | Структурированный log-бэкенд |
| Kafka           | Обработка логов в потоках    |
| AWS CloudWatch  | Облачное лог-хранилище       |
| Datadog, Splunk | SaaS решения                 |

### ⚠️ Возможные проблемы

|Проблема|Решение|
|---|---|
|Потеря логов при сбое|Использовать буферизацию и ретраи|
|Нагрузка на сеть|Настроить фильтрацию и агрегацию|
|Парсинг ошибок|Явно указывать формат логов (JSON лучше текста)|
|Дублирование|Следить за путями и метками|

### 🧩 Агентский сбор + stdout

> Идеальный сценарий в современных приложениях — писать логи в **stdout** в **структурированном виде** (например, JSON), а агент (Fluent Bit, Promtail и др.) собирает их и пересылает куда нужно.

---

### 📌 Когда применять агентский сбор логов

| Когда                         |Почему|
|---|---|
| Много сервисов/хостов         |Централизация и единообразие|
| Используется K8s/[[Docker]]   |stdout + агенты = best practice|
| Нужен анализ и хранение логов |Интеграция с Loki, ELK и др.|
| Хотите не зависеть от кода    |Агент работает независимо от приложений|

---

> 🧠 Приложение должно просто "писать". Обработка, агрегация, доставка — задача агентов. Это соответствует идее разделения ответственности и облегчает CI/CD.
