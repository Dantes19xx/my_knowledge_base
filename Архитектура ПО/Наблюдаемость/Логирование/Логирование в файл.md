##  📂 Логирование в файл

### 🧱 Суть подхода

Логирование в файл означает, что приложение записывает логи в локальные или удалённые файлы (например, `/var/log/app.log`). Этот подход был стандартом в эпоху **монолитных приложений и серверов** с долгим временем жизни.

> Подразумевает, что приложение управляет хранением и организацией логов самостоятельно.

### ✅ Преимущества

| Преимущество | Описание |
|--------------|----------|
| **Совместимость со старыми системами** | Подходит для традиционного окружения: bare-metal или long-running VM. |
| **Разделение по файлам** | Возможность логировать разные уровни (info, error) в разные файлы. |
| **Управляемость** | Можно настроить ротацию, архивирование, локальный просмотр. |

### ⚠️ Недостатки

| Недостаток | Почему это важно |
|------------|------------------|
| ❌ Плохо подходит для контейнеров | Контейнеры эфемерны, и их файловая система может быть недолговечной. |
| ❌ Проблемы с агрегацией | Требуется агент или прослойка для сбора и отправки логов на централизованный сервер. |
| ❌ Утечка места на диске | Без ротации файлы логов могут быстро заполнить диск. |
| ❌ Усложнение CI/CD | Приложение становится менее переносимым между окружениями. |

### 🔧 Реализация

#### Python (logging в файл)

```python
import logging

logging.basicConfig(
    filename='/var/log/myapp.log',
    level=logging.INFO,
    format='%(asctime)s %(levelname)s %(message)s'
)

logging.info("Log entry written to file.")
```

### 🔗 Интеграция с лог-агрегаторами

Чтобы централизованно собирать логи из файлов, часто используются агенты:

| Агент                | Назначение                                                |
| -------------------- | --------------------------------------------------------- |
| Fluentd / Fluent Bit | Чтение и отправка логов в [[Elasticsearch]], Kafka и т.п. |
| Filebeat             | Популярный агент от Elastic Stack                         |
| rsyslog / syslog-ng  | Для пересылки логов на удалённые сервера                  |

### 📌 Когда уместно логирование в файл?

- В старых системах без контейнеризации.
    
- На **bare-metal** или **VM**, где важна устойчивость логов к перезапуску приложения.
    
- Когда лог-файлы являются артефактами аудита, отчётности или локальной диагностики.
    

### 🚫 Когда НЕ уместно?

- В Kubernetes и [[Docker]] ([[stdout]] предпочтительнее).
    
- В serverless и облачных функциях (stdout агрегируется автоматически).
    
- В микросервисной архитектуре, где логи должны быть **централизованы** и **структурированы**.
    

---

> ☝️ Если используешь лог-файлы — убедись, что у тебя есть план их ротации, агрегации и очистки. Само по себе логирование в файл не масштабируется.
