**Шардирование** — это горизонтальное разбиение данных и их распределение между несколькими хранилищами (шардами), как правило — на разных физических/логических серверах.

Каждый **шард** содержит один и тот же набор колонок, но **разные строки**.

📌 Пример:

> В интернет-магазине данные пользователей из разных регионов размещаются в разных шардах. Это уменьшает нагрузку и ускоряет доступ.

---

### 🔑 Основные цели шардирования:

- Масштабирование хранилища и производительности.
    
- Снижение нагрузки на отдельный сервер.
    
- Повышение доступности (через изоляцию).
    
- Устойчивость к сбоям в отдельных шардах.
    
- Улучшение времени отклика в геораспределенных системах.
    

---

### 🧠 Основные методы шардирования

| Метод               | Описание                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| **Хэшированное**    | Данные распределяются по шардам по результату хеш-функции. Пример: `shard_id = hash(user_id) % N`.        |
| **Диапазонное**     | Каждый шард обслуживает определённый диапазон значений (например, даты или цены).                         |
| **Геошардирование** | Данные распределяются по географическим признакам (по странам, регионам и т. д.).                         |
| **Динамическое**    | Автоматическое масштабирование количества шардов в зависимости от нагрузки. Требует системы балансировки. |

---

### 📌 Примеры использования

|Сценарий|Метод шардирования|
|---|---|
|Хранение логов по дате|Диапазонное|
|Пользователи из разных стран|Геошардирование|
|Уникальные ID пользователей или заказов|Хэшированное|
|Неравномерный рост данных|Динамическое|

---

### 📉 Недостатки и сложности

- ✨ **Сложная реализация**: требует продуманной архитектуры.
    
- 🔄 **Решение перекрестных запросов**: JOIN’ы между шардами работают медленно.
    
- ⚠️ **Балансировка нагрузки**: возможна неравномерность, особенно при range-шардировании.
    
- 🔁 **Миграция данных**: добавление новых шардов может потребовать перераспределения данных.
    

---

### 🛠️ Поддержка в популярных СУБД

|СУБД|Поддержка шардирования|
|---|---|
|**MongoDB**|Встроенное шардинг-решение через `mongos`, конфигурационные серверы, балансировщик.|
|**PostgreSQL**|Через расширения (`Citus`, `pg_shard`), нативно с версии 14 — логическое шардирование.|
|**MySQL**|Не поддерживает напрямую, но можно использовать Vitess, ProxySQL и другие решения.|
|**Redis**|Redis Cluster поддерживает автоматическое шардирование по ключу.|

---

### 🧪 Рекомендации

- Используй **естественные ключи**, хорошо распределённые по данным.
    
- Избегай **переусложнённых запросов** между шардами.
    
- Продумывай **стратегию миграции данных** заранее.
    
- Мониторь **нагрузку на шарды** и **автоматизируй балансировку**.
    

---

### 🧾 Заключение

> Шардирование — мощный инструмент масштабирования, но требующий вдумчивого подхода. Это не "включаем и забываем", а архитектурное решение с последствиями на долгие годы.
