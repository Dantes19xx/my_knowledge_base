## 📌 Репликация

✏️ **Репликация** — это создание и поддержание копий базы данных на нескольких серверах для обеспечения отказоустойчивости, масштабируемости и быстрого доступа к данным.

### 🔄 Типы репликации

|Тип|Описание|Особенности/проблемы|
|---|---|---|
|**Master-Slave**|Один главный узел (Master) и один или несколько подчинённых (Slaves).|✔ Подходит для read-heavy приложений  <br>❗ Возможны задержки синхронизации|
|**Multi-Master**|Несколько узлов могут быть главными (принимают записи).|✔ Высокая доступность  <br>❗ Сложность конфликторазрешения и настройки|

---

### 🧭 Репликация master-slave

- **Master** — принимает все операции записи.
    
- **Slaves** — получают изменения и обслуживают запросы только на чтение (read-replica).
    

📌 **Паттерн Read-Replica**:

1. Запись выполняется через мастер.
    
2. Реплики копируют данные.
    
3. Чтения обрабатываются через реплики.
    

**Пример**:  
Пользователь Алиса создаёт заказ — запись идёт в мастер.  
Затем она просматривает историю — чтение с реплики.

🛠 **Проблемы**:

- Задержка репликации
    
- Возможная несогласованность данных
    

**Варианты решений**:

- Направлять критичные к актуальности запросы в мастер
    
- Использовать механизм согласованности (если поддерживается СУБД)
    

---

### 🧭 Репликация multi-master

- Записи возможны с любого узла
    
- Узлы синхронизируются между собой
    
- Используется для высокой доступности и распределённой записи
    

📌 **Преимущества**:

- Обновления с нескольких узлов
    
- Надёжность при сбое одного из узлов
    

⚠️ **Недостатки**:

- Конфликты при одновременной записи
    
- Высокая сложность настройки
    

**Пример**:  
Используется для горячей резервной копии в другом ЦОД, в сочетании с master-slave в основном ЦОД.

---

### 🛠 Репликация в MongoDB

- Настраивается через URI строки подключения и опции чтения
    
- Примерный процесс:
    
    - Первичный сервер анонсирует операцию
        
    - Вторичные подтверждают готовность
        
    - После подтверждения — выполнение записи
        
    - При ошибке — откат
        

---

### 🧬 Репликация в PostgreSQL

|Тип|Описание|
|---|---|
|**Потоковая (streaming)**|Копирует физические данные с использованием WAL (журнал транзакций)|
|**Логическая (logical)**|Оперирует на уровне таблиц, работает по принципу публикация-подписка (с PostgreSQL 10+)|

## ⚡ Кеширование

✏️ **[[Паттерны кеширования|Кеширование]]** — сохранение часто запрашиваемых данных в быстрой памяти, чтобы снизить нагрузку на БД и ускорить отклик.

📥 Паттерн Cache Aside

1. Приложение запрашивает данные → сначала смотрит в кэш
2. Если данных нет → обращается к БД
3. Полученные данные сохраняются в кэш
4. Отдаёт ответ пользователю

### 🌐 Распределённый кеш

- Данные хранятся на нескольких узлах
    
- Могут быть реплицированы и шардированы
    

📌 **[[Redis]]** — один из популярных кешей:

- Разбит на сегменты (минимум 3 для кластера)
    
- У каждого сегмента есть:
    
    - **Master** — принимает запись
        
    - **Slave** — реплика для отказоустойчивости
        
- Возможность до 500 реплик на сегмент (зависит от провайдера, например, AWS)
    

---

## ✅ Итоги

- **Репликация**:
    
    - Повышает отказоустойчивость и масштабируемость.
        
    - Master-Slave — простая схема для чтения.
        
    - Multi-Master — для распределённой записи и высокой доступности.
        
- **Кеширование**:
    
    - Снижает нагрузку на БД и ускоряет ответы.
        
    - Redis — основной инструмент, поддерживает репликацию и шардирование.
        
    - Паттерн Cache Aside — базовая стратегия кэширования.
