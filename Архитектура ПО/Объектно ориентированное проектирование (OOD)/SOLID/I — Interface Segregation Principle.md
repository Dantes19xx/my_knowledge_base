#solid 

**Принцип разделения интерфейсов**

> «Клиенты не должны зависеть от интерфейсов, которые они не используют.»  
> — Роберт Мартин (Uncle Bob)

---

### 📌 Суть:

Интерфейсы (или абстрактные классы) должны быть **узкими и специализированными**, а не широкими и универсальными.

Если объекту нужно только 1 метод из 10, **интерфейс слишком жирный**.  
Нужно **разделить интерфейс** на несколько более мелких, по зонам ответственности.

---

### 🧠 Зачем это важно:

- Позволяет **классам зависеть только от нужных методов**, а не от всего подряд.
    
- Повышает **гибкость** и **тестируемость**.
    
- Изолирует изменения — если ты меняешь один интерфейс, остальные не страдают.
    

---

### ❌ Нарушение ISP — плохой пример:

```python
class WorkerInterface:
    def work(self):
        pass

    def eat(self):
        pass

class Robot(WorkerInterface):
    def work(self):
        print("Robot working")

    def eat(self):
        raise NotImplementedError("Robots don't eat")
```


🔻 Здесь `Robot` **вынужден реализовать метод**, который ему не нужен.  
Это делает интерфейс **слишком общим**, нарушая принцип ISP.

---

### ✅ Соблюдение ISP — хороший пример:

```python
class Workable:
    def work(self):
        pass

class Eatable:
    def eat(self):
        pass

class Human(Workable, Eatable):
    def work(self):
        print("Human working")

    def eat(self):
        print("Human eating")

class Robot(Workable):
    def work(self):
        print("Robot working")
```

🔹 Интерфейсы разделены:

- `Human` реализует оба;
    
- `Robot` — только нужный (`Workable`);
    
- **нет лишней зависимости ни у кого**.

### 📦 В терминах Python:

В Python можно реализовать ISP через **разбиение интерфейсов на отдельные абстрактные классы или `Protocol`**:

```python
from typing import Protocol

class Workable(Protocol):
    def work(self) -> None: ...

class Eatable(Protocol):
    def eat(self) -> None: ...
```

### 🔧 Признаки нарушения ISP:

- Классы реализуют методы, которые им не нужны.
    
- Много `raise NotImplementedError()`.
    
- Часто используются интерфейсы типа `Manager`, `Controller`, `Handler` с кучей несвязанных методов.
    
- Проблемы с тестированием из-за зависимости от ненужных методов.
    

---

### 🧭 Когда особенно полезен ISP:

- В больших системах с множеством ролей и сущностей.
    
- В плагинах, SDK, API — когда нужно давать клиентам **только нужный кусок** функциональности.
    
- При следовании DIP: если интерфейс раздут, ты **не можешь грамотно инвертировать зависимость**.

### 💬 Вывод:

**Interface Segregation Principle (ISP)** говорит:

> «Не заставляй объекты зависеть от методов, которые им не нужны.»

Это делает код:

- **чистым**,
    
- **гибким**,
    
- и **лёгким в сопровождении**.
