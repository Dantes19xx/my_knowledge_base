#solid 

Принцип единственной ответственности

### 📌 Суть:

Каждый класс (или модуль, функция) должен **выполнять одну конкретную задачу** и **отвечать только за один аспект поведения** системы.

Если у класса **две или более причин для изменения**, значит, он нарушает этот принцип.

---

### 🧠 Почему это важно:

- **Прозрачность:** проще читать и понимать код.
    
- **Изменяемость:** изменения не задевают несвязанные части.
    
- **Тестируемость:** можно писать маленькие и точные unit-тесты.
    
- **Переиспользуемость:** класс делает одно — его легко переиспользовать.


### ❌ Нарушение SRP — плохой пример: 

```python
class OrderManager:
    def create_order(self, data):
        # логика создания заказа
        pass

    def save_to_db(self, order):
        # сохранение в базу данных
        pass

    def send_confirmation_email(self, order):
        # отправка email клиенту
        pass
```

Этот класс:

- создаёт заказ,
    
- работает с БД,
    
- занимается отправкой писем.
    

У него **три причины для изменения**:

- бизнес-логика заказа,
    
- смена БД или ORM,
    
- изменение формата письма.


---

### ✅ Соблюдение SRP — хороший пример:

```python
class OrderCreator:
    def create(self, data):
        # логика создания заказа
        return Order(...)

class OrderRepository:
    def save(self, order):
        # сохранение заказа
        pass

class EmailNotifier:
    def send_confirmation(self, order):
        # отправка email
        pass
```

Каждый класс:

- делает **одно дело**,
    
- изменяется **по одной причине**,
    
- легко **тестируется и расширяется**.
    

---

### 🔧 Признаки нарушения SRP:

- Класс делает «и то, и это».
    
- Название класса расплывчатое (`Manager`, `Processor`, `Handler`).
    
- Тесты к классу огромные и сложные.
    
- При изменении одной задачи ты ломаешь другую.
    

---

### 💬 Итого:

**SRP помогает писать чистый, понятный и сопровождаемый код.**  
Это фундаментальный принцип, на котором строятся все остальные из SOLID.
