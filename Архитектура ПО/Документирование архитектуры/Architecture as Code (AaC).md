## Определение
**Architecture as Code (AaC)** — подход, при котором архитектура системы описывается в машиночитаемом текстовом формате и управляется так же, как программный код: через системы контроля версий, автоматизацию и CI/CD.  
Архитектурные описания становятся **единственным источником правды** (Single Source of Truth), из которого можно автоматически генерировать диаграммы, документацию и проверки.

---

## Принципы AaC
1. **Декларативное описание** — архитектура фиксируется в текстовом формате (DSL, YAML, JSON, Markdown).
2. **Хранение в Git** — архитектурные артефакты версионируются и проходят code review.
3. **Автоматическая генерация** — из описания строятся C4-диаграммы, схемы взаимодействия, документация.
4. **Проверка на соответствие стандартам** — автоматические тесты архитектуры (lint, правила соответствия).
5. **Интеграция с разработкой** — изменения в архитектуре синхронны изменениям в кодовой базе.

---

## Связь с C4-моделью
[[Нотация С4|C4-модель]] идеально сочетается с AaC, т.к. её диаграммы можно генерировать из кода:

- **Контекст (System Context)** — фиксируется сущности и связи на верхнем уровне.
- **Контейнеры (Containers)** — описываются модули, сервисы и базы данных.
- **Компоненты (Components)** — детализация сервисов.
- **Код (Code)** — привязка к конкретным реализациям.

**Пример рабочего процесса:**
1. Архитектор пишет описание системы в Structurizr DSL.
2. Код DSL хранится в Git.
3. В CI/CD пайплайне запускается генерация PNG/SVG-диаграмм.
4. Диаграммы автоматически публикуются в Wiki или документацию.

---

## Интеграция с CI/CD

**Типичный пайплайн:**

1. **Commit** архитектурного файла в Git.
    
2. **CI Stage**:
    
    - Запуск линтера (проверка синтаксиса и правил архитектуры).
        
    - Генерация диаграмм (PlantUML, Structurizr CLI).
        
3. **CD Stage**:
    
    - Публикация диаграмм и документации (например, в Confluence, GitHub Pages, Obsidian Vault).
        
    - Уведомление команды о новых изменениях.


---

## Преимущества

- **Актуальность** — архитектура всегда соответствует коду.
    
- **История изменений** — полная прослеживаемость через Git.
    
- **Автоматизация** — минимизация ручной правки диаграмм.
    
- **Прозрачность** — команда видит изменения архитектуры в PR.
    

---

## Недостатки

- Порог входа для архитекторов, не знакомых с Git и DSL.
    
- Для быстрого прототипирования всё ещё удобнее доска и маркер.
    
- Необходима дисциплина при синхронизации кода и архитектуры.
    

---

## Инструменты для AaC

- **Structurizr DSL** — генерация C4-диаграмм.
    
- **C4-PlantUML** — текстовое описание диаграмм C4 в PlantUML.
    
- **Arch-as-code** — набор инструментов и практик для AaC.
    
- **Mermaid.js** — диаграммы в Markdown (подходит для GitHub и Obsidian).
    
- **ADR Tools** — управление архитектурными решениями (Architecture Decision Records).
    

---

## Когда применять

- Сложные системы с долгим жизненным циклом.
    
- Команды с распределённой разработкой.
    
- Проекты с высоким уровнем требований к документации.
    
- Системы, где архитектура часто меняется и должна быть проверяема.
