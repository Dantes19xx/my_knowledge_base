# Безопасность

## Определение

Безопасность в микросервисной архитектуре — это комплекс мер по **защите данных, взаимодействия и инфраструктуры** от несанкционированного доступа, атак и внутренних уязвимостей.

---

## Основные аспекты безопасности

### 1. Аутентификация и авторизация

- **Аутентификация** — подтверждение личности (кто ты?)
- **Авторизация** — проверка прав доступа (что тебе можно?)

**Подходы:**
- JWT (JSON Web Tokens)
- OAuth 2.0 / OpenID Connect
- API Gateway как точка контроля доступа

---

### 2. Безопасность API

- Ограничение доступа к эндпоинтам (например, через роли)
- Проверка входных данных (валидация, ограничения по размеру)
- Ограничение скорости (rate limiting)
- Поддержка HTTPS/TLS

---

### 3. Изоляция сервисов

- Минимизация прав у сервисов (principle of least privilege)
- Использование сетевых политик (NetworkPolicies в Kubernetes)
- Контроль межсервисных коммуникаций (mTLS, [[Service Mesh]])

---

### 4. Шифрование

- **В покое**: данные в базах, файловых хранилищах
- **В передаче**: TLS/SSL для всех внешних и внутренних коммуникаций

---

### 5. Секреты и конфиденциальные данные

- Никогда не хранить пароли и ключи в коде
- Использовать секрет-хранилища:
  - HashiCorp Vault
  - AWS Secrets Manager
  - Kubernetes Secrets (с шифрованием)

---

### 6. Защита CI/CD и инфраструктуры

- Подпись артефактов и образов (например, cosign, Notary)
- Проверка уязвимостей в зависимостях (Snyk, Trivy, OWASP Dependency-Check)
- Ограничение прав сервисов в CI (RBAC, IAM)

---

## Паттерны и практики

- Zero Trust Security (ноль доверия внутри и снаружи)
- Defense in Depth (многоуровневая защита)
- Security-as-Code (политики как код)
- Контейнеризация с безопасными образами (минимальные, без root-доступа)
- Регулярное обновление зависимостей

---

## Проверочные вопросы

- Где и как хранятся секреты?
- Все ли API защищены TLS?
- Есть ли ограничение доступа между сервисами?
- Какие политики доступа настроены на уровне инфраструктуры?
- Какие уязвимости нашли в последнем сканировании зависимостей?

---

## Метрики и наблюдаемость

- Успешные/неуспешные попытки входа
- Подозрительная активность (rate-limiting, brute-force)
- Аномалии в поведении API
- Отчёты сканеров безопасности

---

## Вывод

Безопасность не добавляется в конце — она **встраивается в архитектуру с самого начала**. Микросервисная архитектура требует комплексного подхода: от изоляции и политики доступа до безопасных практик разработки, тестирования и эксплуатации.
