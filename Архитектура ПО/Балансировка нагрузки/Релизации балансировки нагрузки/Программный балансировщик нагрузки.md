# 🧠 Программный балансировщик нагрузки

## 📌 Определение
**Программный балансировщик нагрузки** — это приложение или служба, работающая на уровне программного обеспечения, которая распределяет входящий сетевой трафик между несколькими серверами, чтобы обеспечить высокую доступность, отказоустойчивость и масштабируемость системы.

Он работает на уровне **сетевых протоколов (L4)** и/или **протоколов приложений (L7)**, реализуя алгоритмы маршрутизации запросов.

---

## 🛠️ Примеры популярных программных балансировщиков

| Инструмент       | Уровень | Описание |
|------------------|--------|----------|
| **HAProxy**      | L4/L7  | Высокопроизводительный TCP/HTTP балансировщик |
| **NGINX**        | L7     | Веб-сервер и HTTP-балансировщик |
| **Traefik**      | L7     | Современный HTTP-реверс-прокси с auto-discovery |
| **Envoy Proxy**  | L4/L7  | Прокси от Lyft, заточен под сервис-меш |
| **Apache HTTPD** | L7     | Поддерживает модули для балансировки |

---

## ⚙️ Как работает

1. Клиент отправляет запрос на балансировщик (например, `https://app.example.com`).
2. Балансировщик принимает трафик и решает, на какой сервер отправить запрос, согласно заданному **алгоритму балансировки**.
3. Проксирует запрос к целевому серверу.
4. Получает ответ и пересылает его обратно клиенту.

---

## 🔁 Алгоритмы балансировки

| Алгоритм                  | Описание |
|---------------------------|----------|
| **Round Robin**           | Циклическое распределение запросов |
| **Least Connections**     | Сервер с наименьшим числом текущих соединений |
| **IP Hash**               | Один и тот же клиент → один и тот же сервер |
| **Weighted Round Robin**  | Серверы с большим "весом" получают больше трафика |
| **Random**                | Случайный выбор сервера |

---

## 🧩 Архитектурные схемы

- 🔁 **Reverse Proxy**: Программный балансировщик находится между клиентом и backend-серверами.
- 🧱 **Сервис-меш**: Балансировщик встроен в инфраструктуру (например, с помощью Envoy + Istio).
- ☁️ **Облачный**: Может быть реализован внутри облачного провайдера (например, ELB в AWS, но программно управляемый через API).

---

## ✅ Преимущества

- 💡 **Гибкость и настройка** — можно тонко конфигурировать маршрутизацию, кэш, SSL-терминацию и др.
- 🚀 **Быстрое масштабирование** — легко добавлять/удалять бэкенды без перезапуска.
- 🔒 **Безопасность** — шифрование, защита от DDoS, контроль доступа.
- 🔧 **Интеграция с DevOps** — можно конфигурировать через CI/CD, API, Ansible и т.п.

---

## ❌ Недостатки

- 📉 **Оверхед производительности** — особенно при работе на уровне L7 (разбор HTTP-заголовков).
- ⚙️ **Необходимость настройки и сопровождения** — требует мониторинга и конфигурационного контроля.
- ⚠️ **Точка отказа** — если не настроен в HA-режиме (Active/Passive или Active/Active), может быть SPOF.

---

## 🧠 Когда использовать

- В микросервисной архитектуре — маршрутизация между сервисами.
- Для масштабируемых веб-приложений — распределение HTTP/HTTPS трафика.
- В [[Kubernetes]] — через ingress-контроллер (NGINX, Traefik).
- При развертывании сервисов в Docker Swarm или Nomad.

---

## 📎 Пример конфигурации (NGINX)

```nginx
http {
  upstream backend {
    server app1.example.com;
    server app2.example.com;
  }

  server {
    listen 80;

    location / {
      proxy_pass http://backend;
    }
  }
}
```
