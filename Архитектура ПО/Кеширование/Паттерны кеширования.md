# Cache Aside
1. Пользователь отправляет запрос на чтение данных. Приложение проверяет кеш. Если данные найдены, происходит попадание в кеш.
2. Если данные не найдены, происходит кеш-промах и приложение отправляет запрос к базе данных.
3. Пользователь получает ответ. Данные заносятся в кеш.

**Плюсы Cache-Aside:**

- **Устойчивость к сбоям кеша** Если сервер кеша выходит из строя, система всё равно может работать, обращаясь напрямую к базе данных. Хотя это всё равно нежелательно, ведь увеличение нагрузки на базу данных может привести к выходу её из строя. В таких случаях кеш лучше реплицировать.
- **Модель данных в кеше может отличаться от модели данных в БД** Это позволяет выполнить запрос к БД, объединяющий несколько таблиц, и сохранить его в кеше под одним ключом. Так можно избежать дальнейшего выполнения сложной логики.

**Минусы Cache-Aside**:

- **Низкая скорость** **обновления данных** Обрабатываются только операции чтения, а не записи. Следовательно, любая операция записи всегда будет миновать кеш и выполняться непосредственно в базу данных, что считается медленной операцией.
- **Несогласованность данных в кеше с базой данных** Запись делается в базу данных, но не в кеш — в нём всё ещё старые данные. Чтобы справиться с этим, разработчики обычно используют параметр TTL для содержимого кеша и продолжают отдавать потенциально устаревшие данные до истечения TTL. Если нужно гарантировать свежесть данных, можно вручную инвалидировать кеш, используя одну из стратегий инвалидации, которые рассмотрим позже в этом уроке.

# Read-Through

Различие с паттерном Cache-Aside в том, что актуальные данные из базы данных **сразу** кладутся в кеш и только потом возвращаются приложению.

💡 В паттерне Read-Through к базе данных обращается именно кеш, а не приложение.

**Плюсы Read-Through:**

- **Меньшая сложность приложения и низкая вероятность ошибок**
    
    Кеш не обновляется на стороне приложения — теперь это ответственность базы данных. В стратегии Read-Through кеш является вспомогательным сервисом БД и приложению не нужно обновлять кеш при чтении.
    

**Минусы Read-Through:**

- **Кеш-промах при первом запросе** Когда данные запрашиваются в первый раз, это всегда приводит к кеш-промаху и влечёт за собой дополнительное время на загрузку данных в кеш. Это можно исправить с помощью «прогрева кеша» — ручной отправки запросов на старте приложения, чтобы данные из БД успешно подгрузились в кеш.
- **Ограничения на выбор модели данных в кеше** Модель данных в кеше должна быть идентична модели базы данных.
- **Чувствительность к ошибкам в отличие от Cache-Aside** Из-за того, что к базе обращается не приложение, а кеш, в случае ошибки данные будет брать неоткуда. И вернётся запрос с ошибкой. В паттерне Cache-Aside приложение в случае ошибки само отправит запрос к БД.


 *Cache Aside и Read-Through оптимизируют только операции чтения и подходят для приложений, где практически отсутствуют операции записи. Конечно, это справедливо лишь для малой части реальных приложений.* 


# Refresh-ahead

Описание
**Refresh-ahead** — это паттерн кэширования, при котором данные в кэше обновляются в фоне до того, как они устареют. Это предотвращает задержки, связанные с истечением срока действия данных, обеспечивая всегда быстрый доступ к свежей информации.

 Механизм работы
- При установке значения в кэш указывается TTL (time-to-live).
- До его истечения фоновый процесс заранее обновляет данные.
- Таким образом, клиент всегда получает актуальные данные без задержки.

 Преимущества
- 🔹 Минимальные задержки при чтении.
- 🔹 Кэш почти всегда содержит свежие данные.
- 🔹 Уменьшается вероятность одновременного обращения большого числа клиентов к источнику данных.

Недостатки
- 🔸 Более сложная реализация.
- 🔸 Возможна перегрузка источника данных из-за периодических обновлений.
- 🔸 Ресурсоёмкость: требует фоновых потоков или задач.

Когда использовать
- Данные часто читаются и имеют предсказуемый срок жизни.
- Важно поддерживать высокую производительность и быстрый отклик.
- Допустимо обновлять данные заранее, даже если они могут не понадобиться.

Сравнение с другими паттернами

| Паттерн       | Обновление                       | Пример использования                               |
| ------------- | -------------------------------- | -------------------------------------------------- |
| Lazy-loading  | По запросу при отсутствии данных | Типичный кэш на основе `@lru_cache` в Python       |
| Write-through | При записи                       | Базы данных с кэшом (например, Redis + PostgreSQL) |
| Refresh-ahead | В фоне, до истечения TTL         | Веб-приложения с интенсивным чтением данных        |
| Time-based    | Через фиксированные интервалы    | Мониторинг, аналитика                              |

Пример (общее описание)
- Кэш с TTL = 10 минут.
- Через 8 минут после сохранения данные автоматически обновляются в фоне.
- При обращении клиент получает уже обновлённые данные без задержки.

---

> 💡 *Паттерн Refresh-ahead особенно полезен, когда чтения очень часты, а задержки недопустимы.*



# Write-Through

## Описание
Write-Through — это паттерн, при котором все операции записи сначала проходят через кэш, а затем синхронно записываются в основное хранилище (например, базу данных). Таким образом, кэш всегда содержит актуальные данные, но запись может быть медленнее из-за ожидания подтверждения от хранилища.

## Механизм работы
- Клиент делает запись → сначала обновляется кэш → затем данные записываются в базу.
- Запись в хранилище блокирует клиента до завершения операции.
- Чтение происходит напрямую из кэша.

## Преимущества
- Кэш всегда содержит последнюю версию данных.
- Упрощается логика кэширования — не нужно отслеживать консистентность вручную.
- Хорошо работает в системах, где чтений больше, чем записей.

## Недостатки
- Запись медленнее, чем при использовании чистого кэша.
- Возможны проблемы при сбоях (например, запись в кэш удалась, но в БД — нет).
- Высокая нагрузка на базу при большом количестве записей.

## Когда использовать
- Необходимо обеспечить консистентность между кэшем и хранилищем.
- Объём записей невелик, или задержки допустимы.
- Преобладают операции чтения, а не записи.

## Пример использования
- Кэш Redis + PostgreSQL.
- Новая запись пользователя сначала пишется в Redis, затем — в PostgreSQL.
- Все последующие чтения идут из Redis.

# Write-Behind (Write-Back)

## Описание
Write-Behind — это паттерн, при котором запись сначала сохраняется только в кэш, а в основное хранилище отправляется с задержкой, асинхронно и в фоне. Это ускоряет запись, но увеличивает риск потери данных при сбоях.

## Механизм работы
- Клиент делает запись → данные сохраняются в кэше.
- Отложенная синхронная или пакетная запись в базу данных происходит позже, в фоновом процессе.
- Чтения происходят из кэша, пока данные не выгружены в хранилище.

## Преимущества
- Быстрая запись (низкие задержки).
- Возможность объединения нескольких операций в одну (batch update).
- Снижение нагрузки на хранилище.

## Недостатки
- Возможна потеря данных при сбоях кэша до записи в базу.
- Требует сложной логики управления очередями и обработкой ошибок.
- Кэш и база данных могут временно содержать разные данные (временная неконсистентность).

## Когда использовать
- Допустим временный разрыв консистентности.
- Важна высокая производительность записи.
- Приложение может повторно попытаться записать данные при сбоях.

## Пример использования
- Данные заказов пишутся в Redis, а затем каждые 5 секунд синхронно выгружаются в PostgreSQL.
- Потоковый процессинг с Apache Kafka или очереди типа RabbitMQ для буферизации.
