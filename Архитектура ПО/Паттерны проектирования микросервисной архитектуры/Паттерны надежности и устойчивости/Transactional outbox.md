### Проблема

В распределённых системах, когда сервис выполняет изменение в базе данных и должен опубликовать событие (например, в Kafka, RabbitMQ и т.д.), возникает проблема **несогласованности данных**:

- Транзакция в БД может завершиться успешно, а отправка события — нет.
    
- Или наоборот: событие отправлено, а транзакция с данными откатилась.
    

Это приводит к **рассинхронизации** между сервисами.

---

### Решение

Вместо прямой отправки события в брокер сообщений, **записываем событие в таблицу `outbox` в той же транзакции, что и изменение основной таблицы**. Затем отдельный процесс (изолированный компонент) читает из `outbox` и отправляет сообщение в брокер.

Суть реализации заключается в том, что сервис, который должен отправить сообщение или событие, сначала сохраняет его в базе данных как часть транзакции, в рамках которой он создаёт, удаляет или обновляет бизнес-сущность. При этом сохранение этого сообщения происходит в отдельную outbox-таблицу. Из неё отдельный процесс потом их вычитывает и отправляет через брокер сообщений.

Фактически решение состоит в том, чтобы разделить один процесс на два, изолировав операции взаимодействия с внешними системами друг от друга.

---

### Компоненты

|Компонент|Описание|
|---|---|
|Основная таблица|Таблица, в которую вносятся изменения (например, `orders`, `users` и т.п.)|
|Outbox таблица|Таблица, в которую записываются события (например, `outbox_events`)|
|Outbox-процессор|Отдельный сервис или background job, который читает события из outbox и публикует их|
|Message broker|Kafka, RabbitMQ и др. — принимает события из outbox|


---
## Пример структуры таблицы `outbox`

```sql
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY,
    aggregate_type TEXT,
    aggregate_id TEXT,
    event_type TEXT,
    payload JSONB,
    occurred_at TIMESTAMP,
    processed BOOLEAN DEFAULT FALSE
);
```


### Пример использования

#### 1. Транзакция:

```sql
BEGIN;

-- Изменяем данные
INSERT INTO orders (id, status) VALUES ('123', 'CREATED');

-- Логируем событие
INSERT INTO outbox_events (
    id, aggregate_type, aggregate_id, event_type, payload, occurred_at
) VALUES (
    gen_random_uuid(), 'Order', '123', 'OrderCreated',
    '{"order_id": "123", "status": "CREATED"}',
    NOW()
);

COMMIT;
```

#### 2. Отправка

Фоновый процесс:

```python
def outbox_worker():
    events = db.query("SELECT * FROM outbox_events WHERE processed = FALSE")
    for event in events:
        try:
            broker.publish(event.event_type, event.payload)
            db.query("UPDATE outbox_events SET processed = TRUE WHERE id = %s", (event.id,))
        except Exception:
            log.error("Ошибка при отправке события", event.id)
```


---
### Преимущества

- Гарантированная доставка событий (once-at-least delivery)
    
- Устойчивость к сбоям
    
- Согласованность между данными и событиями
    
- Нет необходимости в распределённых транзакциях
    

---

### Недостатки

- Необходимость ручного управления outbox таблицей (очистка, мониторинг)
    
- Увеличение задержки между коммитом и фактической отправкой
    
- Потенциальные дубли при сбоях (нужна idempotency в потребителях)
    

---

### Смежные паттерны

- **Change Data Capture (CDC)** — альтернатива, особенно при использовании Debezium
    
- **Idempotent Consumer** — для обработки возможных дублирующихся сообщений
    
- **[[Retry]] Pattern** — для повторной отправки событий
