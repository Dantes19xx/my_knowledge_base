**[[API Gateway]] as a Bottleneck** — антипаттерн микросервисной архитектуры, при котором чрезмерная нагрузка, логика и ответственность сосредоточены в одном API-шлюзе, превращая его в узкое место системы. В результате это снижает отказоустойчивость, замедляет работу системы и нарушает принцип разделения ответственности.

---

### Признаки

- **API Gateway содержит бизнес-логику**, которая должна быть распределена по сервисам.
    
- **Все клиентские запросы проходят через один шлюз**, независимо от их характера.
    
- **Падение API Gateway приводит к недоступности всей системы**.
    
- **Увеличение времени ответа** при росте количества маршрутов и правил маршрутизации.
    
- **Сложность сопровождения**: шлюз становится монолитом, в котором сложно ориентироваться.
    
- **Трудности с масштабированием**: API Gateway становится централизованным ограничением пропускной способности.
    

---

### Причины возникновения

- Отсутствие архитектурного контроля за развитием API Gateway.
    
- Попытка централизовать кэширование, авторизацию, валидацию, агрегацию и маршрутизацию в одном месте.
    
- Желание "ускорить разработку", внедряя логику прямо в шлюз.
    
- Отсутствие разграничения между инфраструктурной и бизнес-логикой.
    

---

### Последствия

- **Потеря гибкости и расширяемости** API-шлюза.
    
- **Централизованный Single Point of Failure (SPOF)**.
    
- **Снижение производительности всей системы**.
    
- **Рост времени отклика для клиентов**.
    
- **Зависимость развития системы от одной команды, обслуживающей API Gateway**.
    

---

### Как избежать

| Подход                                                        | Описание                                                                                |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Минимизировать ответственность шлюза                          | API Gateway должен выполнять только маршрутизацию, аутентификацию и базовую валидацию.  |
| Делегировать бизнес-логику в микросервисы                     | Не реализовывать бизнес-процессы в шлюзе.                                               |
| Использовать несколько шлюзов при необходимости               | Разделить API Gateway по доменным зонам или типам клиентов (например, мобильные / веб). |
| Горизонтальное масштабирование                                | Обеспечить отказоустойчивость через масштабирование шлюза.                              |
| Мониторинг производительности шлюза                           | Метрики по количеству вызовов, времени ответа, ошибкам.                                 |
| Использовать [[BFF]] (Backend for Frontend) при необходимости | Создавать узкоспециализированные фасады для разных клиентов, а не расширять один шлюз.  |

---

### Заключение

API Gateway — важный компонент микросервисной архитектуры, но при неправильном использовании он превращается в критическую точку отказа и замедляет развитие всей системы. Этот антипаттерн напоминает: шлюз — это транспортный и сетевой слой, а не контейнер бизнес-логики.
