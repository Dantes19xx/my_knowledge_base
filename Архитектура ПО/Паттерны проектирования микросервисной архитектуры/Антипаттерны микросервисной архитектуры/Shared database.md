# 🧱 Архитектурный паттерн: Shared Database

## Описание
**Shared Database** — это паттерн, при котором несколько микросервисов используют одну и ту же базу данных. Все сервисы имеют доступ к общим таблицам, что позволяет выполнять кросс-сервисные запросы и транзакции, но создаёт высокую связанность и риски при масштабировании.

---

## Цели и задачи
- Упростить начальную реализацию микросервисов.
- Сохранить возможность использовать JOIN и транзакции между сервисами.
- Избежать дублирования данных.

---

## Отличия от [[Database per Service|Database per Service]]
| Характеристика       | Shared Database     | Database per Service |
| -------------------- | ------------------- | -------------------- |
| Архитектура          | Централизованная БД | Децентрализованная   |
| Изоляция             | Отсутствует         | Полная               |
| Тип СУБД             | Общая для всех      | Индивидуальная       |
| Расширяемость        | Ограничена          | Высокая              |
| Независимость команд | Низкая              | Высокая              |
| Масштабирование      | Сложное             | Простое и гибкое     |

---

## Преимущества
- Легко реализовать бизнес-логику с использованием SQL JOIN.
- Простая интеграция между сервисами.
- Общая модель данных ускоряет разработку.
- Подходит для старта (особенно при миграции от монолита).

---

## Недостатки
- Высокая связанность сервисов через схему БД.
- Изменения в БД могут повлиять на все сервисы.
- Миграции становятся координированными и рискованными.
- Проблемы с масштабированием и отказоустойчивостью.
- Нарушение принципа "сервис владеет своими данными".

---

## Когда использовать
- При миграции от монолита к микросервисам — как временное решение.
- В проектах с жёсткими сроками, где важно быстро запустить функциональность.
- При отсутствии сильных требований к масштабированию и изоляции.

---

## Типовые технологии

| СУБД             | Подходит для Shared DB                                |
|------------------|--------------------------------------------------------|
| PostgreSQL       | Да (широкая поддержка транзакций, типов, функций)     |
| MySQL / MariaDB  | Да                                                     |
| Microsoft SQL    | Да                                                     |

---

## Примеры использования
1. **Миграция от монолита**: сервисы постепенно выделяются, но продолжают использовать общую БД.
2. **Проекты MVP**: для экономии времени и ресурсов сервисы работают с общей схемой.
3. **Финансовые системы**: используют транзакции на уровне БД между подсистемами.

---

## Практические советы
- Разделяй схемы БД по namespace или префиксам, если сервисы используют одну СУБД.
- Используй **read-only доступ** там, где возможны конфликты изменений.
- Внедряй слой доступа к данным (DAO, ORM), чтобы упростить миграцию в `Database per Service`.
- Старайся избегать бизнес-логики в БД (триггеры, процедуры) — они затрудняют отделение сервисов.
- В долгосрочной перспективе планируй переход на [[Database per Service]].

---

## Часто используется совместно с
- [[API Gateway|API Gateway]] — общий доступ через централизованный шлюз.
- Монолитная архитектура — часто как промежуточный этап.
- Слоем сервисов внутри монолита для разграничения ответственности.
