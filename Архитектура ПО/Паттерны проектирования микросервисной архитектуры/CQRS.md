# CQRS (Command Query Responsibility Segregation)

## Определение
**CQRS** — это архитектурный паттерн, разделяющий ответственность за:
- **Чтение данных (Query)** — операции, которые не изменяют состояние системы
- **Изменение данных (Command)** — операции, которые изменяют состояние, но не возвращают данных

## Цель паттерна
Разделить модели для чтения и записи, чтобы упростить логику, повысить производительность и масштабируемость системы.

## Принцип работы
- Команды изменяют данные (через обработчики команд)
- Запросы читают данные (через отдельные обработчики/репозитории)
- Часто используются разные модели и источники данных для чтения и записи

## Пример
```plaintext
[Client]
   |         
   |--- Command ---> [Command Handler] ---> [Write Model / DB]
   |
   |--- Query -----> [Query Handler]   ---> [Read Model / DB]
```

  ## Преимущества CQRS

- **Разделение ответственности**  
  Чтение и запись разделены, код становится чище и проще в поддержке.

- **Масштабируемость**  
  Можно независимо масштабировать части, отвечающие за чтение и запись.

- **Оптимизация моделей**  
  Read и Write модели можно проектировать независимо, под конкретные задачи.

- **Производительность**  
  Read-модель может быть упрощена и оптимизирована для быстрых запросов.

- **Гибкость хранения данных**  
  Возможность использовать разные базы данных или структуры хранения для чтения и записи.

---

## Недостатки CQRS

- **Сложность архитектуры**  
  Увеличивается количество компонентов, инфраструктура становится сложнее.

- **Проблемы консистентности**  
  Требуется обеспечить eventual consistency между write и read моделями.

- **Необходимость синхронизации**  
  Требуются механизмы обновления read-модели после изменений в write-модели.

- **Избыточность кода**  
  Появляется больше шаблонного кода: команды, обработчики, модели, мапперы и т.д.

- **Избыточно для простых приложений**  
  В проектах без сложной бизнес-логики может создать ненужную сложность.

---

## Где применять CQRS

- Системы с **высокой нагрузкой** на чтение или запись
- Приложения с **сложной бизнес-логикой** и разными правилами для чтения и записи
- Архитектура на базе **[[DDD]] (Domain-Driven Design)**
- **Финансовые системы**, где важно отслеживать каждое изменение
- **Микросервисные архитектуры**, где важно разделение ответственности

---

## Часто используется вместе с

- **Event Sourcing**  
  События становятся источником истины, а состояние агрегатов восстанавливается из истории событий.

- **Message Broker (Kafka, RabbitMQ и др.)**  
  Для доставки команд и событий между компонентами.

- **Read/Write базы данных**  
  Использование разных баз или схем: например PostgreSQL для записи и [[Elasticsearch]] для чтения.

- **Микросервисы**  
  CQRS помогает изолировать ответственность и уменьшить связанность компонентов.

- **Saga / Orchestration Patterns**  
  Для координации долгоживущих транзакций в распределённых системах.
