## Паттерны управления данными в микросервисах

Каждый микросервис должен владеть своими данными. Управление данными — ключ к изоляции, отказоустойчивости и согласованности.

---

### 1. Database per Service

| Характеристика       | Описание |
|----------------------|----------|
| Суть                 | Каждый микросервис использует свою отдельную базу данных. |
| Пример               | Сервис заказов — PostgreSQL, сервис уведомлений — MongoDB. |
| Когда применять      | Почти всегда — это рекомендуемый подход. |
| Плюсы                | Изоляция данных, масштабируемость, независимое развитие. |
| Минусы               | Сложность в кросс-сервисных запросах и транзакциях. |

---

### 2. Shared Database (не рекомендуется)

| Характеристика       | Описание |
|----------------------|----------|
| Суть                 | Несколько микросервисов используют одну и ту же БД. |
| Пример               | Все сервисы пишут в общую PostgreSQL базу. |
| Когда применять      | Только как временное решение при миграции из монолита. |
| Плюсы                | Простота реализации. |
| Минусы               | Нарушение изоляции, tight coupling, конфликт при изменениях схемы. |

---

### 3. Event Sourcing

| Характеристика       | Описание |
|----------------------|----------|
| Суть                 | Все изменения состояния сохраняются как события. Текущее состояние восстанавливается из них. |
| Пример               | `OrderCreated`, `OrderPaid`, `OrderShipped`. |
| Когда применять      | Для сложных бизнес-доменов с аудитом и историей. |
| Плюсы                | Полная история, гибкость в восстановлении состояния. |
| Минусы               | Сложность реализации, нужны механизмы реплея событий. |

---

### 4. CQRS (Command Query Responsibility Segregation)

| Характеристика  | Описание                                                                |
| --------------- | ----------------------------------------------------------------------- |
| Суть            | Разделение модели чтения и записи.                                      |
| Пример          | Пишем в одну модель (PostgreSQL), читаем из другой ([[Elasticsearch]]). |
| Когда применять | Когда сильно различаются требования к чтению и записи.                  |
| Плюсы           | Оптимизация под задачи, масштабируемость.                               |
| Минусы          | Сложность синхронизации, дублирование логики.                           |

---

### Сравнение

| Критерий              | Database per Service | Shared DB    | Event Sourcing    | CQRS                  |
|-----------------------|----------------------|--------------|-------------------|------------------------|
| Изоляция данных       | Высокая              | Низкая       | Высокая           | Средняя               |
| Подходит для          | Большинство случаев  | Переходный этап | Аудит, сложная логика | Высокая нагрузка, оптимизация |
| Сложность реализации  | Низкая/Средняя       | Низкая       | Высокая           | Средняя/Высокая        |
| Историчность данных   | Нет                  | Нет          | Да                | Возможно (с событиями) |
