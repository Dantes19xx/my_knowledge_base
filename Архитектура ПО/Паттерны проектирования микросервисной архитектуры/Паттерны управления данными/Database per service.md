# 🧱 Архитектурный паттерн: Database per Service

## Описание
**Database per Service** — это паттерн, при котором каждый микросервис владеет своей собственной базой данных и не имеет прямого доступа к базам других сервисов. Это гарантирует изоляцию данных, независимость сервисов и упрощает масштабирование.

---

## Цели и задачи
- Обеспечить независимость микросервисов.
- Снизить связанность и точку отказа.
- Позволить каждой команде использовать наиболее подходящую СУБД.
- Улучшить масштабируемость и отказоустойчивость.

---

## Отличия от общей БД
| Характеристика         | Shared Database                     | Database per Service                   |
|------------------------|--------------------------------------|----------------------------------------|
| Владелец данных         | Общий                                | Каждый сервис                          |
| Тип СУБД                | Одинаковый                           | Может различаться                      |
| Изоляция               | Слабая                               | Полная                                 |
| Миграции               | Сложные, централизованные            | Изолированные, управляются отдельно    |
| Связи между таблицами  | Внешние ключи                        | Нет внешних ключей между сервисами     |

---

## Преимущества
- Сервисы можно разрабатывать, масштабировать и деплоить независимо.
- Возможность выбора оптимальной СУБД под нужды сервиса (SQL, NoSQL, TimeSeries и т.д.).
- Улучшенная изоляция сбоев — один сервис не влияет на другие напрямую.
- Упрощение управления правами доступа.

---

## Недостатки
- Сложности с реализацией запросов, охватывающих несколько сервисов.
- Требуется дополнительная реализация консистентности (через события или саги).
- Повышение сложности DevOps (несколько БД, резервное копирование и мониторинг).
- Невозможно использовать JOIN между таблицами разных сервисов.

---

## Когда использовать
- При переходе от монолита к микросервисам.
- Когда важна независимость и изоляция данных.
- Если команды работают независимо и используют разные технологии.
- При высоких требованиях к отказоустойчивости.

---

## Типовые технологии

| Тип данных     | Возможные СУБД                                |
|----------------|-----------------------------------------------|
| Реляционные    | PostgreSQL, MySQL, Microsoft SQL Server       |
| Документные    | MongoDB, Couchbase                            |
| Графовые       | Neo4j, ArangoDB                               |
| Временные      | TimescaleDB, InfluxDB                         |

---

## Примеры использования
1. **E-commerce**: сервис заказов использует PostgreSQL, а сервис рекомендаций — MongoDB.
2. **SaaS-платформа**: у каждого микросервиса своя БД, что позволяет масштабировать их независимо.
3. **Мобильное API**: сервис профилей, уведомлений и сообщений работают с разными хранилищами, заточенными под специфику данных.

---

## Практические советы
- Не допускай прямых SQL-запросов между сервисами — используй API или события.
- Храни идентификаторы внешних сущностей как ссылки (reference by ID), но не как связи.
- Для согласованности данных между сервисами используй **[[Event-Driven Architecture (EDA)|event-driven]] подход** или **saga pattern**.
- Обеспечь резервное копирование и мониторинг каждой БД отдельно.
- Используй миграции внутри сервиса (например, Alembic, Flyway) — не глобально.

---
