# Event Sourcing

**Event Sourcing** — это архитектурный паттерн, при котором состояние объекта (или агрегата) сохраняется не в виде текущих значений, а как последовательность событий, которые к этому состоянию привели.

---

## Основная идея

Вместо хранения текущего состояния, система хранит **все события**, произошедшие с объектом. Текущее состояние вычисляется путём **реплея событий** (replay) с самого начала.

---

## Пример

Вместо хранения:

```json
{
  "user_id": "123",
  "balance": 500
}
```

```json

[
  { "event": "AccountCreated", "user_id": "123", "initial_balance": 0 },
  { "event": "MoneyDeposited", "amount": 300 },
  { "event": "MoneyDeposited", "amount": 200 }
]
```

## Компоненты

| Компонент         | Описание                                                                 |
|-------------------|--------------------------------------------------------------------------|
| **Event**         | Событие, описывающее изменение состояния (например, `OrderPlaced`).      |
| **Event Store**   | Хранилище событий (обычно логически упорядоченное).                      |
| **Aggregate**     | Объект, восстанавливающий состояние на основе событий.                   |
| **Command**       | Намерение пользователя (например, `DepositMoney`), которое вызывает событие. |
| **Projector**     | Создаёт проекцию текущего состояния на основе событий (для чтения).      |

---

## Преимущества

- **Полная история изменений** — можно "отмотать" время назад или отладить.
- **Аудит** — всё, что произошло, зафиксировано.
- **Лёгкая интеграция с [[CQRS]]** — разные модели для чтения и записи.
- **Поддержка сложной бизнес-логики и инвариантов**.

---

## Недостатки

- Повышенная **сложность реализации**
- Трудности с **миграцией схемы событий**
- Неудобство при **поиске и агрегации данных**
- Необходимость **проекторов для чтения**

---

## Когда применять

- Бизнес-домен с критичной **аудитностью**
- Необходимость **воспроизводимости и отладки**
- Используется **[[CQRS]]** или микросервисная архитектура
- Сложные бизнес-инварианты, которые легче выразить через события

---

## Когда избегать

- Простые CRUD-приложения
- Проекты с ограниченными ресурсами на поддержку инфраструктуры
- Когда история изменений не важна

---

## В связке с [[DDD]]

| Компонент DDD     | Как используется в Event Sourcing                                  |
|-------------------|---------------------------------------------------------------------|
| **Aggregate**     | Хранит и применяет события, а не изменяет напрямую состояние.       |
| **Repository**    | Загружает агрегат, воспроизводя (replay) его события.              |
| **Domain Events** | События отражают реальные бизнес-события и фиксируются в хранилище. |
