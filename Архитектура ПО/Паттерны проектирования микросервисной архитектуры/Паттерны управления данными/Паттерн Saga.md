## Что такое Saga

**Saga** — это архитектурный паттерн для управления распределёнными транзакциями в микросервисных системах. Он обеспечивает целостность данных и управление ошибками при выполнении долговременных бизнес-процессов, которые включают несколько микросервисов.

## Контекст: проблема распределённых транзакций

Традиционные транзакции подчиняются требованиям **ACID**:

- **Atomicity** — атомарность
    
- **Consistency** — целостность
    
- **Isolation** — изолированность
    
- **Durability** — надёжность
    

В микросервисной архитектуре выполнение одной транзакции может затрагивать несколько сервисов и баз данных, что делает использование стандартных ACID-транзакций невозможным. **Saga** решает эту проблему через цепочку **локальных транзакций** с компенсирующими действиями.

## Подход Saga: как работает

Saga разбивает глобальную транзакцию на серию локальных шагов (действий), которые выполняются разными микросервисами. Если один из шагов завершился с ошибкой, система вызывает **компенсирующие действия** для отката уже выполненных шагов.

### Способы реализации Saga

1. **Оркестрация (Orchestration)**  
    Один центральный **сервис-оркестратор** управляет порядком вызовов шагов и компенсирующих действий.
    
2. **Хореография (Choreography)**  
    Сервисы обмениваются **событиями**, координация происходит децентрализованно.
    

## Реализация ACID-принципов в паттерне Saga

|Свойство|Как реализуется в Saga|
|---|---|
|Атомарность|Каждый шаг — локальная транзакция. Атомарность достигается за счёт выполнения компенсирующих действий.|
|Целостность|Поддерживается логикой отмены и компенсирующих операций. Требуется согласованность статуса между сервисами.|
|Изолированность|Часто не достигается полностью. Возможны состояния временной неконсистентности.|
|Надёжность|Зависит от надёжности хранения состояния и выполнения компенсирующих действий.|

## Обработка ошибок и компенсации

### 1. Компенсационные транзакции

Откатывают уже совершённые действия в случае неудачного завершения одного из следующих шагов. Требуют чёткого определения логики отмены.

### 2. Повторные попытки ([[Retry|Retries]])

Используются при временных сбоях (например, сетевые ошибки). Настраиваются интервалы и количество попыток.

### 3. [[Timeout|Тайм-ауты и дедлайны]]

Для каждой операции устанавливается максимальное время выполнения. После его истечения вызывается ошибка и инициируется откат.

### 4. [[Circuit Breaker]]

Останавливает попытки взаимодействия с неисправным сервисом после превышения порога неудач. Используется для защиты от лавинообразных сбоев.

### 5. [[Event bus|Событийно-ориентированная обработка ошибок]]

Ошибки публикуются в виде событий (например, `OrderFailed`), и другие микросервисы принимают решение об откате.

### 6. Мониторинг и алерты

Системы мониторинга ([[Prometheus]], [[Grafana]], [[ELK|ElasticStack]]) отслеживают метрики и ошибки. Алерты обеспечивают оперативную реакцию.

## Шаги внедрения паттерна Saga

### Шаг 1. Анализ бизнес-процесса

- Разделить процесс на шаги, каждый из которых выполняется отдельным микросервисом.
    
- Для каждого шага определить:
    
    - Основное действие (`do`)
        
    - Компенсирующее действие (`undo`)
        

### Шаг 2. Проектирование микросервисов

- Создать микросервисы с чётко определёнными API.
    
- Добавить отдельные API для выполнения компенсирующих операций.
    
- Обеспечить **идемпотентность** всех операций.
    

### Шаг 3. Управление состоянием

- Хранить состояние каждой локальной транзакции в своей БД.
    
- Сохранять статус выполнения, уникальный ID и текущий шаг.
    
- Выбрать способ координации: оркестратор или событийная шина.
    

### Шаг 4. Реализация действий и компенсаций

- Реализовать `do`-операции: они должны быть идемпотентны, опираться на ID и статус.
    
- Реализовать `undo`-операции по тем же принципам.
    
- Гарантировать, что повторный вызов не приведёт к дублированию.
    

### Шаг 5. Логирование и мониторинг

- Ввести расширенное логирование всех транзакций и их шагов.
    
- Настроить систему сбора логов (например, EFK/ELK).
    
- Подключить систему метрик и алертов.
    

### Шаг 6. Тестирование

- Написать unit-тесты для каждого шага:
    
    - Проверка `do`-действий
        
    - Проверка `undo`-действий
        
- Дополнительно можно реализовать интеграционные тесты, покрывающие всю последовательность шагов.

## Краткий пересказ

- Паттерн **Saga** применяется в микросервисах для управления распределёнными транзакциями.
    
- Он заменяет глобальные транзакции последовательностью **локальных транзакций**.
    
- Ошибки обрабатываются через **компенсационные действия**, **повторные попытки**, **тайм-ауты**, **Circuit Breaker**, **события** и **мониторинг**.
    
- Реализация требует чёткого проектирования, хранения состояния, идемпотентности и логирования.
    
- Saga может быть реализована через **оркестрацию** или **хореографию**.
