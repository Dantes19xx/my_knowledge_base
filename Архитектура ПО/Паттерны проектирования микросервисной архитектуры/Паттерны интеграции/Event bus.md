# 🧱 Архитектурный паттерн: Event Bus (Событийная шина)

## Описание
**Event Bus** — это паттерн взаимодействия компонентов системы через события. Вместо прямых вызовов между сервисами или модулями, они публикуют события на общую шину, а подписчики (другие компоненты) реагируют на них. Это снижает связанность компонентов и упрощает масштабирование.

---

## Цели и задачи
- Ослабить связность между модулями/сервисами.
- Упростить расширение системы без изменений существующего кода.
- Обеспечить масштабируемую и гибкую коммуникацию.
- Поддержать асинхронное взаимодействие и реактивную архитектуру.

---

## Отличие от очередей сообщений
| Характеристика      | Event Bus                                       | Очередь сообщений (Message Queue)          |
| ------------------- | ----------------------------------------------- | ------------------------------------------ |
| Направление         | Один → Много (pub/sub)                          | Один → Один                                |
| Подписка            | Подписчики получают копии                       | Один потребитель получает сообщение        |
| Надёжность доставки | Завист от реализации (чаще "по лучшему усилию") | Часто гарантированная доставка (ack/retry) |
| Используется для    | Событий, уведомлений                            | Задач, команд (job-based)                  |

---

## Преимущества
- Компоненты не знают друг о друге напрямую.
- Лёгкое добавление новых потребителей.
- Расширяемость и гибкость.
- Отлично работает с микросервисной и реактивной архитектурой.

---

## Недостатки
- Трудности отладки и трассировки событий.
- Потеря сообщений возможна без надёжной реализации.
- Сложность в обеспечении последовательности и согласованности.
- Возможность “забвения” о неиспользуемых событиях (мусор).
---

## Когда использовать
- Когда важно слабое связывание между компонентами.
- При необходимости масштабируемых событий (например, [[Подходы к логированию|логирование]], нотификации, аудит).
- Для реактивных систем и архитектуры, основанной на событиях.
- Если планируется дальнейшее расширение логики без изменения источника событий.

---

## Типовые технологии

| Категория       | Примеры                                                            |
| ------------------------ | ------------------------------------------------------------------ |
| **Брокеры событий** | Apache Kafka, NATS, RabbitMQ (в режиме pub/sub), [[Redis]] Streams |
| **Event Bus библиотеки** | MediatR (.NET), EventEmitter (Node.js), RxJS                       |
| **Cloud решения** | AWS EventBridge, Google Pub/Sub, Azure Event Grid                  |

---

## Примеры использования
1. **E-commerce**: сервис заказов публикует `OrderCreated`, а другие сервисы (уведомления, начисления, аналитика) подписаны на это событие.
2. **Микросервис “Профиль пользователя”**: при обновлении профиля публикуется `UserProfileUpdated`, которое ловит сервис логирования и уведомлений.
3. **IoT**: устройства отправляют события в центральную шину, где они обрабатываются разными обработчиками (хранение, алерты, визуализация).

---

## Практические советы
- Делай события неизменяемыми (immutable) — публикуй факт, а не команду.
- Названия событий должны быть в прошедшем времени (`OrderPlaced`, `UserDeleted`).
- Храни схему событий (JSON Schema, Avro, Protobuf) для совместимости.
- Добавляй `correlation_id` в события для трассировки.
- Используй ретрансляцию событий (event replay), если это критично для консистентности.

---

## Часто используется совместно с
- **[[Event Sourcing]]**: события становятся источником правды.
- **[[CQRS]]**: команда меняет состояние, событие обновляет read-модель.
- **Saga**: для координации долгих процессов через события.
