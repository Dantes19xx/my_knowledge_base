## Зачем нужен быстрый релиз

Быстрый релиз — это не просто ускорение работы. Это возможность оперативно реагировать на запросы клиентов, адаптироваться под изменения на рынке и быстрее внедрять улучшения. CI/CD позволяет выпускать качественный продукт чаще и надёжнее.

---

## Что такое CI/CD

CI/CD (Continuous Integration / Continuous Delivery / Continuous Deployment) — это набор практик и методологий, направленных на автоматизацию всех этапов жизненного цикла разработки ПО: от написания кода до его развертывания в рабочей среде.

---

## Предпосылки CI/CD

- **Планирование (Plan)**: формулировка требований, создание задач, распределение работы.
    
- **Разработка (Code)**: написание кода, подготовка коммитов и пул-реквестов.
    

---

## Continuous Integration (CI)

Цель CI — автоматическое и частое объединение изменений кода в общий репозиторий с обязательной проверкой на ошибки.

**Этапы:**

1. **Работа с системой контроля версий**
    
    - Изменения коммитятся в Git.
        
    - Используются пул-реквесты и review-процессы.
        
2. **Сборка (Build)**
    
    - После коммита запускается сборка проекта.
        
    - Проверка на совместимость и работоспособность.
        
3. **Автоматическое тестирование**
    
    - Запускаются юнит-тесты, интеграционные и e2e-тесты.
        
    - Тесты выявляют баги на раннем этапе.
        

---

## Continuous Delivery (CD)

Цель CD — всегда быть готовыми к выпуску обновлений.

**Этапы:**

1. **Подготовка к релизу (Release)**
    
    - Проверка качества.
        
    - Генерация артефактов ([[Docker]]-образы, deb-файлы, архивы и пр.)
        
2. **Развертывание в тестовые среды (Staging/Pre-prod)**
    
    - Автоматическая доставка в промежуточные среды.
        
    - Дополнительные smoke-тесты, UI-тесты.
        

---

## Continuous Deployment

Расширение Continuous Delivery: если все этапы CI/CD пройдены, изменения автоматически попадают в продуктив.

**Этап:**

- **Автоматическое развертывание (Production Deployment)**
    
    - Нет ручного подтверждения.
        
    - Нужно быть уверенным в качестве всего пайплайна.


---
## Конвейер CI/CD

**CI/CD Pipeline** — последовательность этапов автоматизации:

```
Plan → Code → Build → Test → Release → Deploy
```

Каждый этап запускается автоматически при выполнении предыдущего. Это позволяет команде быстрее выпускать обновления и сократить число ошибок при развёртывании.

## Pipeline as Code (PaC)

Подход, при котором пайплайн описывается в виде кода (например, `.gitlab-ci.yml`, `Jenkinsfile`, `azure-pipelines.yml`) и хранится рядом с исходным кодом проекта.

**Преимущества:**

- Историчность: видно, кто и когда изменил пайплайн.
    
- Версионирование: пайплайн можно тестировать вместе с кодом.
    
- Масштабируемость: упрощает работу в больших проектах.
    
- Инфраструктура как код (IaC): PaC — один из её компонентов.

## DevOps и CI/CD

**DevOps** — методология, объединяющая разработку и эксплуатацию. CI/CD — инструмент реализации DevOps-культуры.

**Ключевые принципы DevOps:**

- Совместная ответственность за продукт.
    
- Автоматизация процессов.
    
- Непрерывное улучшение.
    
- Быстрая обратная связь.

## Выводы

- CI/CD — это фундамент современного подхода к разработке.
    
- Он снижает количество багов, ускоряет релизы и делает разработку предсказуемой.
    
- Настроенный CI/CD позволяет команде сосредоточиться на качестве продукта, а не на рутинных задачах.
